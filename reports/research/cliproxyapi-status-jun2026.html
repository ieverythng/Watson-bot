Known Issues and Pitfalls

⚠ Gotchas

  • Upstream repo down: g13y/CLIProxyAPI returns 404. Use the fork at ieverythng/CLIProxyAPI.
  • No releases available: GitHub Releases return 404 (9-byte = 404 page). The pre-built binary in the repo is the only option.
  • WSL auth flow: Background processes expire during OAuth waits. Must use foreground/PTY mode with -no-browser flag.
  • Cloudflare blocks browser automation: Do NOT attempt to use Hermes browser tools against chatgpt.com — Cloudflare challenge page blocks immediately.
  • Rate limits still apply: ChatGPT Plus has usage caps (~100 messages/3 hours on GPT-5). CLIProxyAPI does not bypass these.
  • Port choice: Config uses 8317 (not default 4950) to avoid conflicts. Adjust Hermes config accordingly.
  • Local inference backend: WatsonMain uses the Windows-hosted llama.cpp server at http://172.24.16.1:8080/v1; do not route qwen36-turbo-hermes through CLIProxyAPI.
  • Go not installed on WSL: Cannot build from source without installing Go first. Use the pre-built binary.
  • v7 command syntax: Auth is cliproxyapi -codex-login, NOT cliproxyapi login. Server is cliproxyapi serve, NOT cliproxyapi start.

How It Works (Architecture)

📥 Data Flow

Hermes Agent (WatsonMain)
    │
    ├── Local/default inference
    │     HTTP POST /v1/chat/completions
    │     ▼
    │   llama.cpp server (Windows host, 172.24.16.1:8080/v1)
    │     qwen36-turbo-hermes
    │
    └── Premium/delegated inference
          HTTP POST /v1/chat/completions
          API Key: "watson-chatgpt-key"
          ▼
        CLIProxyAPI (localhost:8317, PID 3319)
          │
          │ OAuth-authenticated request to OpenAI
          │ (uses Codex OAuth tokens stored in ~/.cli-proxy-api/)
          ▼
        OpenAI ChatGPT/Codex Backend
          │
          │ GPT-5.5 / GPT-5.4 / codex-auto-review response
          ▼
        CLIProxyAPI → Hermes Agent

CLIProxyAPI exposes a standard OpenAI-compatible API for ChatGPT/Codex models. The local Watson inference backend is separately served by llama.cpp on the Windows host at http://172.24.16.1:8080/v1.

Existing OAuth Access (Hermes Built-in)

🎯 Note: Hermes Already Has Codex OAuth

Hermes Agent already has a built-in openai-codex provider with OAuth authentication. This is currently used for:

  • Vision (auxiliary): gpt-5.4-mini via openai-codex
  • Delegation: gpt-5.5 via chatgpt-plus (CLIProxyAPI)

CLIProxyAPI adds value by exposing additional models (GPT-5.5, codex-auto-review, gpt-image-2) that may not be available through Hermes' built-in Codex OAuth, and by providing a standalone proxy endpoint that any OpenAI-compatible client can use independently.

Key difference: Hermes' built-in Codex OAuth uses the Codex CLI authentication flow. CLIProxyAPI uses its own OAuth implementation with multi-account pooling, model routing, and a full API surface.

Multi-Account / Multi-Session

🔄 Scaling Options

CLIProxyAPI supports:

  • Multiple accounts: Add more OAuth sessions for round-robin load balancing across accounts
  • Multiple providers: Same proxy can serve ChatGPT, Claude Code, Gemini CLI, and Grok Build simultaneously
  • Multi-session: Each OAuth session is independent — you can have parallel conversations through the same proxy
